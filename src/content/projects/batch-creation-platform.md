## 业务场景与负责事项

批量投放需要根据一份模板，在多个广告主下创建计划、广告组和创意。配置包含创建数量、命名规则、预算、定向、标题和素材；每个对象都可能单独创建失败。

我参与快手、B站、广点通的批创后端实现与后续修复。个人提交覆盖媒体对象、预览、提交、素材处理及重提逻辑。下面分别记录模板展开、B站提交顺序，以及广点通的状态和事务修复。

## 预览阶段：模板展开成本地草稿

以 B站为例，preview 校验配置并处理模板，根据广告主和创建数量生成计划、单元、创意，保存为本地对象。命名规则和素材、标题分配在展开时执行，返回 batchId 与预览列表。

本地计划与单元、单元与创意通过绑定 ID 关联。用户确认预览后，提交阶段据此读取同一批草稿。广点通还提供已有广告组的预览和提交入口，需要读取原对象再装配新的创意配置。

**预览不创建媒体投放对象，但会写入本地模板和草稿。** 因此预览失败要关注本地事务回滚。

## B站提交：上游成功后才提交下游

MediaBilibiliBatchCreateServiceImpl.commit 的执行顺序如下：

1. 读取批次创意，按广告主汇总并去重视频素材，执行媒体上传。
2. 读取本地计划，调用媒体创建接口，保存媒体 campaignId、成功标记和失败原因。
3. 只有拿到有效 campaignId 才处理其下的单元；单元成功后保存媒体 unitId。
4. 只有拿到有效 unitId 才创建对应创意，回写每个创意的成功或失败结果。
5. 更新本地对象，返回计划、单元和创意结果；按参数决定是否保留模板。

返回结果能够区分失败发生在哪一层。素材上传位于计划提交之前，若上传阶段直接抛错，流程可能尚未进入逐对象结果回写。

代码另有计划、单元等重提入口，按本地对象 ID 读取记录继续提交。本地 ID 不能替代媒体端幂等能力；外部创建成功而本地没有记录时，仍可能需要核对媒体实际对象。

## 广点通：提交状态与创建结果分别记录

2026 年 1 月的修改增加“提交中”状态，并优化创意重新提交。创意对象定义了 commit 的三个值：0 未提交、1 提交成功、2 提交中；同时另有 success 和 reason 表示媒体创建结果。

当前异常分支也会把 commit 写为 1，再把 success 设为 false 并保存原因。**所以不能只看到名为“提交成功”的状态常量就判定媒体对象创建成功。** 排查时还要看 success、媒体 ID 和 reason。

素材处理中，已有媒体映射时复用视频、封面 ID；不存在映射时从 OSS 取文件上传，再维护资源关系。标题、图片列表、视频比例和封面属于创意组件装配，需要按媒体要求处理。

## 广点通预览：修复事务上下文与异常传播

2026 年 2 月的修复删除了异常分支中对 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 的调用，并把已有广告组预览入口的 @Transactional 调整为 @DSTransactional。

原代码在多数据源事务内查找 Spring 本地事务状态，可能产生另一层异常，掩盖原始预览失败原因。修改后，由对应事务框架处理回滚，异常分支记录并抛出错误。这个提交解决的是预览异常传播与事务上下文，验证范围也应围绕这两个入口。
