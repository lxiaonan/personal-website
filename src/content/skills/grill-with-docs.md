## 它是干什么的

`grill-with-docs` 可以理解为带项目记忆的需求讨论：一边追问方案，一边把真正有长期价值的共识写入文档。当前版本会组合 `grilling` 和 `domain-modeling` 两项能力。

核心不是多写几份说明，而是解决两个常见问题：同一个词在产品和代码里含义不同；已经权衡过的方案，在下一次开发或新的 AI 会话里又被重新争论。

## 会留下哪些内容

- **领域词汇表 `GLOSSARY.md`。** 记录业务概念及其明确含义，例如“预扣积分”“最终结算”“任务租约”。词汇表关注概念，不应该塞进函数调用和技术实现细节。
- **架构决策记录 ADR。** 通常放在 `docs/adr/`，描述背景、候选方案、最终选择、原因及后果。
- **已澄清的方案。** 形成边界清晰的开发输入；如需 PRD 或实施规格，应明确提出，让 Agent 按项目约定另行整理。

文档按需创建。一次简单讨论可能只补充几个术语，并不一定产生 ADR。当前上游建议仅为难以逆转、缺少背景会令人困惑、且存在真实取舍的决定记录 ADR。

## 安装与准备

```bash
npx skills add mattpocock/skills
```

选择 `grill-with-docs`、`grilling`、`domain-modeling`；也可以安装完整技能包。对于新代码库，建议先运行 `setup-matt-pocock-skills`，约定文档位置和事项跟踪方式。

调用前告诉 AI 项目目录、已有文档，以及你希望讨论的具体变化。已有 `GLOSSARY.md` 和 ADR 时，应该先读取再讨论，避免创建冲突的词义或重复决策。

## 一个后端开发示例

```text
使用 grill-with-docs 推敲视频生成任务的退款方案。
现状：提交任务时预扣积分，第三方异步回调结果，失败时需要退款。
请先读取现有术语表和 ADR，再追问超时、重复回调、重试和部分成功的处理。
讨论中统一“失败”“超时”“取消”的业务含义。
对有长期影响的决策记录 ADR，避免把临时想法写成已确定方案。
```

这个例子中，最有价值的追问可能是：“轮询超时”是否等于“第三方任务失败”？如果不是，立即退款可能导致最终成功后仍然免费。先把词义和状态边界弄清楚，再选退款机制，会比直接生成代码更可靠。

## 推荐使用顺序

1. 阅读项目约定、词汇表和相关 ADR。
2. 分轮讨论目标、约束和异常场景，区分事实、假设与用户选择。
3. 术语明确后及时更新词汇表；重要取舍明确后记录 ADR。
4. 讨论结束时核对文档变更和仍未解决的问题。
5. 将确认后的行为交给实现与测试流程，例如使用 `tdd` 逐个验证关键路径。

## 有什么实际收益

新成员和新的 AI 会话能更快理解项目语言；后续重构可以看到“当初为什么这么做”；需求、代码、测试名称也更容易保持一致。对退款、账务、异步任务、幂等这类概念密集的后端功能尤其有帮助。

## 使用时需要留意

它会涉及项目文件写入，开始前应说明允许修改哪些文档。AI 提出的推荐仍然需要由项目负责人判断；术语表也不应成为未经确认需求的存放处。上游路径与组合能力会变化，安装后应核对同一版本的配套 Skill。
