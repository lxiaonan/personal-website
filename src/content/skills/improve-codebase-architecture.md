## 它是干什么的

这个 Skill 用于审视代码库，寻找值得深入设计的重构机会。重点是模块深度：调用者是否能通过一个相对简单的接口，获得足够完整的能力，而复杂细节由模块内部承担。

例如视频任务的租约、重试、状态迁移和退款判断散落在多个入口，改一条规则需要同步修改许多文件。它会分析这些理解与修改成本，判断是否值得把同一业务概念收拢到更明确的模块里。

## 它关注哪些信号

- 理解一个概念必须在许多小文件之间来回跳转。
- 某个封装接口几乎和内部实现一样复杂，调用者仍要理解所有细节。
- 测试只能依靠大量内部 mock，真实错误却发生在模块组合处。
- 同一类规则在不同入口重复，修改经常遗漏联动位置。
- 近期提交反复触及相同区域，说明这里可能存在持续维护成本。

它会使用“删除测试”等设计判断：如果删掉某层抽象，只是把同样的复杂度搬到别处，这个抽象可能没有提供足够价值。文件数量多或类名长，本身不足以证明需要重构。

## 推荐调用方式

```text
使用 improve-codebase-architecture 检查视频任务模块。
重点关注提交、轮询、超时重试与积分退款之间的重复判断。
请先读取相关 ADR、术语表和近期提交，给出有具体文件依据的重构候选。
输出调整前后的结构图、测试边界与建议优先级。
先做报告，选定候选后再讨论实现。
```

## 一次完整使用会产出什么

1. **范围判断。** 优先看用户指定的痛点；未指定时，从提交历史中的活跃区域寻找线索。
2. **现状证据。** 指出涉及的文件、模块、调用关系，以及实际造成的理解或维护困难。
3. **候选报告。** 当前上游要求生成独立 HTML 报告，展示问题、方案、收益、前后结构图和推荐强度。
4. **选择一个候选。** 用户决定本次值得投入哪一项，避免同时展开大规模重构。
5. **深入设计。** 讨论接口、约束、保留的行为与测试方式，必要时更新术语和 ADR。

## 对后端项目的实际作用

在批量投放系统里，各渠道可能都有“构造请求、提交、解析错误、写回结果”的步骤，但媒体限制并不相同。好的架构分析会区分真正共用的流程与渠道特有规则，而不是因为代码看起来相似就强行统一。

你可以要求 AI 对每项候选回答：这次重构具体让哪类修改更容易？哪些测试能在内部实现变化后继续保留？收益只是减少行数，还是减少了调用者必须知道的事情？

## 使用边界

它首先是一项调查和设计工作，生成报告不表示代码已经重构完成。优先级取决于真实变更频率、风险与收益；冷门且稳定的模块，可能不值得仅为“更漂亮”而修改。

候选若与已有 ADR 冲突，应先说明为什么现在值得重新考虑。确定实施后，建议先为已有外部行为补足必要验证，再逐步调整，最后通过接口级测试和实际运行核对兼容性。
