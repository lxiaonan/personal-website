## 它是干什么的

`tdd` 把测试驱动开发的方法交给 AI：先为一个需要的行为写出会失败的测试，再写最小实现让测试通过，然后进入下一项行为。这样每一步都有运行反馈，避免一次生成大量代码后才发现方向错误。

它强调测试对外可观察的行为。例如“同一个回调重复到达只退款一次”，比“某个私有方法调用了两次”更接近真正需要保证的业务规则。内部结构调整后，只要行为不变，好的测试仍应成立。

## 适合用在哪些地方

- 新增有明确规则的功能，例如优惠计算、幂等请求和任务状态流转。
- 修复可以稳定复现的缺陷，先写回归测试证明问题存在。
- 调整核心模块，希望通过外部接口验证行为兼容。
- 希望 AI 一边实现，一边展示实际运行结果。

只改静态文案、样式间距等低影响内容时，构建检查和浏览器验收通常更合适。TDD 的价值取决于测试是否能揭示重要错误。

## 安装与准备

```bash
npx skills add mattpocock/skills
```

选择 `tdd` 并保留随附的测试与 mocking 参考文件；需要讨论模块设计时，可配套安装 `codebase-design`。它不会自带所有语言的测试运行环境，需要使用项目已有的 JUnit、Vitest、pytest 等工具。

当前上游要求先与用户确认要测试的公开边界，也就是从哪里输入、在哪里观察结果。开始前应说明要覆盖哪些关键路径，以及这些测试无法证明什么。

## 一个可以直接使用的提示词

```text
使用 tdd 修复重复回调导致重复退款的问题。
先阅读项目现有测试与退款接口，提出要验证的公开边界并和我确认。
验收行为：相同任务连续收到两次失败回调，只产生一次有效退款；
已经成功的任务收到迟到失败回调，不改变结算结果。
每次只完成一个行为：展示测试为什么失败，再写最小实现并运行验证。
沿用现有测试框架，避免为了测试暴露私有方法。
```

## 红绿循环如何推进

1. **列出行为与测试边界。** 明确调用入口、输入、可观察结果和依赖范围。
2. **Red：先失败。** 写一个最小用例并运行，确认失败来自缺失或错误行为，而不是语法、环境或连接问题。
3. **Green：最小实现。** 只实现通过当前用例需要的逻辑，并实际运行测试。
4. **下一条行为。** 根据刚获得的反馈选择下一例，不要先批量写完所有假想测试。
5. **评审与重构。** 核对重复与结构问题，重构后再运行相关验证。

经典 TDD 常写作“Red → Green → Refactor”。当前这份 Skill 将实现阶段定义为小步红绿循环，并把重构安排在后续评审阶段；使用时应以安装版本的实际约定为准。

## 好测试是什么样的

预期结果应来自业务规则、独立算例或已确认规格。退款测试应该检查通过公开接口可观察的最终结果；并发幂等还需要覆盖真实并发或合适的集成场景，两个连续请求不能证明数据库竞争已被解决。

应避免断言私有调用顺序、为所有内部协作者写 mock，以及照抄实现公式计算预期值。这些测试可能很绿，但对真正的错误不敏感。

## 怎样判断完成

要求 AI 交付：新增了哪些行为用例、观察到了什么失败、实现后运行了什么命令、结果如何、哪些路径尚未覆盖。测试全绿仅说明已运行用例通过，仍需类型检查、构建、必要的集成测试和人工验收共同判断。
