最难解释的失败，发生在模型已经回答之后：外部调用成功了，系统却在追加扣款时告诉用户余额不足。用户拿不到回答，平台还要承担已经产生的模型成本。

## S · 背景：失败发生在成功之后

固定费用时，调用前扣一次积分就够了。改成 Token 计费后，最终费用要等服务商返回 usage 才知道。

沿用「先扣少量固定费用，成功后再补差额」，就把支付风险留到了不可逆的外部调用之后。**这里需要调整的是时间线，而不只是扣款公式。**

## T · 目标：先确定最多愿意承担多少成本

修复要满足两件事：余额不足时不调用服务商；服务商已经成功时，不因补扣失败隐藏结果。

我的工作是把这些规则转成可检查的分支，再推进实现与契约调整。输入估算、最大输出和结算必须使用同一套边界。

## A · 行动：把预扣、输出上限和结算接起来

### 1. 调用前形成预扣额度

估算输入费用，加上受约束的最大输出费用。余额不够就提前拒绝。服务商请求同时传最大输出 Token 参数，否则本地预算只是一个没有约束力的数字。

### 2. 返回之后分四种情况

| 服务商结果 | 结算动作 | 用户结果 |
| --- | --- | --- |
| 成功，费用低于预扣 | 按实际费用结算，退回差额 | 保留回答 |
| 成功，费用高于预扣 | 按预扣上限封顶 | 保留回答 |
| 成功，没有 usage | 使用配置的固定回退费用 | 保留回答 |
| 调用异常 | 退回预扣，记录退款状态 | 返回失败原因 |

### 3. 验收同时看账本和调用次数

只检查 HTTP 成功会漏掉关键问题。应核对余额、交易金额、退款状态和服务商调用次数，尤其是「余额不足仍然调用」与「外部成功却被本地改成失败」两条反例。

## R · 结果：修好了结算路径，也明确了平台的成本责任

2026-07-10 的提交 `c79dc1205` 包含计费实现、服务商参数映射、测试和契约文档。可确认的交付是预扣与结算逻辑的调整。

**封顶是一项产品取舍：超出预扣的成本由平台承担。** 输入估算并不保证等于服务商账单，因此还需要持续核对估算与实际用量。

下一次设计按用量收费的功能，可以先问：真实费用在哪一步才知道？在那之前，谁承担预算失控的风险？
