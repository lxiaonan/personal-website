提交批创后页面超时，用户又点了一次。服务端该拦住第二次，还是返回第一次的进度？这篇以批创为设计推演，讨论如何让重试回到同一个业务结果。

## S · 背景：用户看到超时，外部系统可能已经成功

一次批创会创建多个投放对象，再调用媒体接口。本地请求没有返回，不代表媒体端没有执行。网关重试、消息重投和人工补跑都会制造类似的不确定性。

只防按钮连点，覆盖不了这些入口。

## T · 目标：重复动作得到同一结论，新动作仍可提交

先定义「同一次提交」的身份，再规定处理中、成功、部分成功时怎样回应。第二次请求最好能拿到已有任务和结果，而不是只有一句「重复请求」。

同一模板发起新的一批投放，可能是合法的新动作。幂等键不能简单由用户 ID 或模板内容决定。

## A · 行动：把标识、状态和数据库约束串起来

### 1. 持久化动作标识

例如先生成提交批次号，让接口、任务和媒体结果都关联它。这里的批次号是设计示例，实际字段要以业务系统为准。

### 2. 状态决定重试语义

| 当前状态（示例） | 相同请求的处理 |
| --- | --- |
| COMMITTING | 返回已有任务与进度 |
| SUCCESS | 返回已有结果 |
| PART_SUCCESS | 展示明细，重提只针对失败项 |
| FAILED | 依据失败类型决定是否可重试 |

数据库更新需要带上预期状态。下面的订单 SQL 仅示意条件更新：

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = ? AND status = 'CREATED';
```

影响行数为零时要查询当前状态，区分重复操作、非法流转与数据异常。

### 3. 约束覆盖并发，补偿复用同一入口

唯一索引作为持久化防线，捕获冲突后查询已存在的结果。缓存或锁可以降低争抢，但不能替代它。补偿也要按原动作身份执行。

## R · 结果：验收看结果，尤其看外部不确定窗口

这是一套方案，不是对某次事故收益的统计。验收应让两个相同请求并发到达、让成功响应丢失、让批次部分成功，然后核对任务数、业务记录和外部对象。

若服务商不支持幂等键或结果查询，本地唯一约束仍无法完全消除「外部成功、本地未记录」窗口。这时需要核对或补偿流程。

**幂等的完成标准是重试之后还能解释结果。**
