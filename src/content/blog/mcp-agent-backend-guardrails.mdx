想让 Agent 查一个任务，最省事的接口似乎是 executeSql。省掉的是工具设计，增加的却是系统暴露范围。先问清业务动作，往往能让工具更小。

## S · 背景：模型读到的内容，可能影响下一次工具选择

网页、文档和用户输入都可能进入上下文。若工具接受任意 SQL、路径或命令，模型生成参数就会直接影响底层系统。

MCP 提供标准连接协议，不替业务系统决定用户可以读哪个项目、修改哪个对象。本文给出接入方案，不是已上线能力清单。

## T · 目标：能做必要的事，也能解释每次调用

内部助手先查询批创结果或分群进度。工具范围、参数上限、用户身份与返回数据都要明确。

产生副作用的工具需要可追踪操作身份与结果，还要有关闭与灰度能力。

## A · 行动：业务动作收口，服务端保持裁决

| 宽泛能力 | 更明确的设计示例 |
| --- | --- |
| executeSql | 查询指定批次结果 |
| 任意文件读取 | 读取允许访问的知识库文档 |
| 任意后台操作 | 重提一个已确认批次的失败项 |

### 校验不依赖模型自觉

检查项目、租户、对象归属、枚举与时间范围。即使模型要求“查询所有项目”，服务端仍按登录用户的实际范围处理。

### 审计记录决策需要的信息

关联用户、会话、工具名与版本、参数摘要、权限结果、耗时和业务结果。秘密与媒体正文不应原样进入审计。

### 错误面向后续行动

返回状态、是否可重试和可读原因，避免将 SQL、堆栈和底层配置交给模型。

### 分阶段开放并可撤回

先只读，验证范围与质量；再考虑可追踪后台动作。副作用操作沿用业务权限、幂等与审计，不因换了协议就绕开。

## R · 结果：误调用时，系统仍然守住范围

以跨项目 ID、过大时间范围、越权工具和外部文档诱导调用为验收样例。检查调用是否被拒绝、审计是否可追踪、模型解释是否符合真实结果。

工具版本变化也要能回溯，必要时关闭单个工具。**连接成功只是接入开始，业务约束成立才有条件扩大开放范围。**
