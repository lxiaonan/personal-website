同一个 Mapper，只换几个筛选参数，为什么查询范围和耗时就完全不同？动态 SQL 的风险往往藏在条件组合里，肉眼读 XML 很难看全。

## S · 背景：可选条件增加了隐含的查询语义

事件、时间、标签、分群、虚拟属性和维表过滤混在一起，每个 if 都有自己的默认行为。空集合若直接跳过 IN，可能把「没有可访问对象」变成「查询全部」。

这篇以后台与 BI 查询为场景推演；具体执行计划必须在目标数据库上核对。

## T · 目标：输入含义稳定，SQL 结果可以预期

先定义 null、空集合、空字符串和默认时间范围分别代表什么。不可访问与未筛选不能混为一谈。

字段、排序方向、过滤操作符也需要服务端白名单，不能把用户传入的字段名直接拼入 SQL。

## A · 行动：在 Mapper 之前先收拢复杂度

### Java 层归一化输入

处理时间、枚举、分页、字段来源与集合大小，再把明确的内部结构交给 Mapper。参数值绑定与标识符白名单分别处理不同风险。

### 把复杂分析移到语义层

普通列表可以使用 MyBatis 条件表达；复杂路径分析则先解析字段来源和依赖，再由 Planner / Builder 分段生成 SQL。不要让所有语义藏在 XML 里。

### 典型组合要拿到最终 SQL

| 参数组合 | 应检查什么 |
| --- | --- |
| 单条件、短时间范围 | 过滤是否生效，扫描范围 |
| 空集合 | 空结果或明确拒绝，不能意外查全部 |
| 大 IN 列表 | 是否拒绝、分片或转中间表 |
| 虚拟属性加维表过滤 | 字段来源与 join 关系 |
| 动态排序加分页 | 白名单、稳定排序与执行计划 |
| 导出 | 限制、去重与查询范围 |

记录查询指纹、参数摘要、耗时和 traceId，敏感参数需要脱敏。执行计划关注过滤、扫描、连接与排序，不只关注有没有索引名。

## R · 结果：可解释性先于优化结论

验证同一输入稳定生成预期 SQL，再检查结果语义与执行计划。数据库类型不同，优化手段也不同，不能用一套索引建议覆盖所有分析引擎。

这篇给出检查矩阵；没有压测数据时，不宣称某种拆分必然更快。**能解释最终查询了什么，才有可靠的调优起点。**
