一个「提交批创」方法，从几十行长成几百行，为什么改一个媒体字段就让人紧张？目录可以很整齐，真正的边界却可能仍然挤在同一个方法里。

## S · 背景：接口里面，混着不同性质的工作

读取模板、校验参数、分配素材、生成名称、创建广告、调用媒体、保存关系、统计失败，全都可能出现在一个提交入口。

这些工作变化频率和失败方式不同。这篇借批创流程讨论分层方案，不把示例类名当作项目现有结构。

## T · 目标：从方法名就能判断会发生什么

预览不产生媒体端副作用，提交才真实创建对象；失败重提只操作允许重试的明细。每层需要可独立定位问题，而不是层层转发同一段逻辑。

环境配置与业务规则也要分开，避免为了调整限流或超时修改核心编排。

## A · 行动：围绕动作分层，而不是围绕 CRUD 堆代码

| 边界 | 负责什么 | 不应承担什么 |
| --- | --- | --- |
| Controller | 协议、入口校验、身份传递 | 全部业务编排 |
| Application Service | 预览、提交、失败重提 | 媒体协议细节 |
| Builder | 配置到本地投放对象 | 真实外部调用 |
| Media Client | 参数适配、超时、媒体错误 | 决定业务终态 |
| Repository / Mapper | 持久化与条件更新 | 用户流程解释 |

### 预览先确定将创建什么

展示对象数量、素材分配、名称和缺失字段，再允许提交。服务端提交时仍要重新校验版本与权限，不能信任旧预览。

### 异常表达业务上能采取的动作

参数错误指出字段；媒体失败保留可读原因；部分成功给出明细；系统异常记录 traceId。不要将所有异常压成一个失败字符串。

### 外部约束通过配置接管

API 地址、超时、限流、批量大小、重试上限和能力开关外置，敏感信息通过环境或配置系统管理。

## R · 结果：边界好不好，看下一次修改

可以用三个问题验收：接一个新媒体时是否主要修改适配层；媒体调用失败时能否定位阶段与对象；不连接真实媒体时能否验证对象构建和业务状态。

不一定一次大重构。先隔离副作用和状态流转，再逐步收拢旧入口。**分层的价值体现在修改与排查过程里。**
