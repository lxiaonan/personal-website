路径图里点一个节点、点「流失」、点「更多」，看起来都是下钻，后端却在回答三种不同问题。把它们都变成临时 SQL 字符串，语义很容易越改越散。

## S · 背景：页面自由配置，后台却需要确定语义

时间范围、分析主体、候选事件、过滤条件和路径步数共同决定查询。节点下钻寻找命中者，流失需要说明停止在哪一步，更多通常涉及未展示节点集合。

现有项目有路径分析与结果分群交付记录；本文讨论其中可复用的规划思路，示例阶段名不视为生产源码摘录。

## T · 目标：同一份配置能解释、下钻并复现

主图与下钻不能各自发明一套筛选含义。保存结果分群后，也要知道这批用户来自什么配置、什么切片与什么时间窗口。

候选事件数、过滤数、时间跨度和导出规模需要可控。

## A · 行动：从页面配置走到语义，再走到 SQL

### 1. 归一化字段与切片

解析事件字段、用户字段、虚拟属性与维表来源。切片记录当前节点、后续节点、更多桶排除集合和分析主体，消除界面参数的歧义。

### 2. 用 CTE 说明每个计算阶段

下面仅示意分段，不是可直接执行的 SQL：

```text
base_events → session_events → path_nodes → slice_users
项目 / 时间过滤   会话与排序      节点展开      人群去重
```

尽早缩小数据范围，再进入窗口计算。每段能单独查看数据规模，比一整条无法解释的 SQL 更便于排查。

### 3. 保存完整定义，不保存预览页

保存分群时核对预览 LIMIT、用户去重、来源参数、创建人和计算时间。发布结果避免让读者看到写到一半的集合。

### 4. 护栏与观测一起设计

记录查询身份、配置快照、耗时与 traceId；针对大范围 join、窗口排序和过滤下推检查执行计划。

## R · 结果：从一组可手算路径验证语义

准备少量用户事件，覆盖重复事件、时间窗口边界、节点命中、流失和更多桶。核对主图与下钻，再保存并刷新分群，确认结果定义仍可复现。

CTE 让查询可解释，不保证引擎一定更快。性能改善要结合 StarRocks 执行计划和数据规模测量。

**Planner 的职责是收拢语义，让同一个问题始终得到同一种解释。**
