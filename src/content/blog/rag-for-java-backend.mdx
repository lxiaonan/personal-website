助手把排查步骤讲得很顺，点开引用却是旧版接口文档。再改提示词，未必能修好这个问题：需要先查模型拿到的资料。

## S · 背景：内部知识既有版本，也有访问范围

媒体对接、BI 口径、错误码和上线流程都会变。通用模型不知道当前项目约定，向量检索也不自动知道哪份文档最新、谁可以读取。

这篇是内部研发助手的方案推演，不表示当前个人 AI 平台已交付完整 RAG 系统。

## T · 目标：回答能回溯到允许访问的证据

用户不仅要知道怎么做，还要知道依据在哪、是否适用于当前版本。证据不足时，应补充检索或说明缺口。

权限在检索与上下文准备阶段落实，不能等敏感内容进入模型后再要求它不要说。

## A · 行动：让每段证据都有身份

### 按用途切分文档

接口文档按接口，指标文档按口径，故障复盘按原因与处理阶段切分。保留标题路径、文档 ID、版本与链接，避免片段脱离上下文。

### 关键词与语义召回互补

“批创”“错误码”之类专有名词需要精确命中，语义检索补充近义表达。检索范围先受项目、权限和有效版本约束，重排与上下文组装仍只接收可访问片段。

### 引用连到真实片段

回答中的链接由检索证据构造并校验，而不是任由模型编造。删除或更新文档时，索引也需要相应更新。

### 固定问题集让迭代可比较

| 问题类型 | 核对重点 |
| --- | --- |
| 明确错误码 | 是否命中正确说明 |
| 旧版与新版并存 | 是否使用适用版本 |
| 用户没有文档权限 | 是否避免进入上下文 |
| 知识库没有答案 | 是否承认证据不足 |
| 多文档排查 | 关键步骤与引用是否完整 |

## R · 结果：分别评价检索与生成

先检查召回文档，再检查回答是否遵守证据。如果正确资料未被召回，优先修检索；如果证据正确但答案错误，再查上下文与生成。

记录来源命中、关键答案点和无依据回答，不把更长、更流畅当成改善。连接 Agent 时，查询资料与执行动作还需要独立边界。

**RAG 的可信度要从证据链验证。**
