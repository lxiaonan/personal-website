下载一份 ID 文件，再原样上传，为什么用户反而匹配不上了？这次问题没有出在查询条件，而是导入过程把 CSV 的格式符号当成了 ID。

## S · 背景：看起来一样的 ID，数据库里已经不同

CSV 下载侧用双引号包裹字段，字段里的双引号则用两个双引号转义。旧导入实现按逗号拆分再 trim，于是 `"00123"` 连同外层引号一起进入结果表。

字段含逗号时，直接 split 还会拆错列；Excel 导出的 UTF-8 BOM 则可能藏在第一个 ID 前。它们都是同一类问题：**文件表示没有被正确还原成业务值。**

## T · 目标：还原格式，但不能改掉用户的值

全局删除引号看似能修复样例，却会破坏 `say "hi"` 这样的真实值。前导零也必须保留，不能把 ID 当数字。

这次目标是收拢 ID 标签与分群的共同解析规则，让相同文件在不同入口得到一致结果。

## A · 行动：先画出边界，再共享解析逻辑

共用工具 `IdCsvFieldSupport` 承担四个动作：

1. 找到引号外的第一个逗号，保留字段内部逗号。
2. 只剥掉首尾成对的双引号。
3. 将内部连续两个双引号还原成一个。
4. 显式处理首部 BOM。

下面是解释边界的输入示例：

| 文件中的字段 | 期望业务值 | 为什么 |
| --- | --- | --- |
| `00123` | `00123` | 前导零是 ID 的一部分 |
| `"00123"` | `00123` | 外层引号属于格式 |
| `"user,west"` | `user,west` | 引号内逗号不是分隔符 |
| `"say ""hi"""` | `say "hi"` | 还原转义，保留真实引号 |

单边引号不能凭猜测删除。验收还要覆盖带 BOM 的首字段，以及标签和分群两个入口。

## R · 结果：修复覆盖两个入口，解析范围也有边界

2026-10-09 的提交 `d8f092647` 对应这次共用解析修复。它解决的是 ID 数据的导入边界，不是一个覆盖所有 CSV 特性的通用解析器；多行字段等场景不在当前工具范围内。

最值得留下的验证方法是：**把系统自己导出的文件，再交给系统自己导入。** 裸值样例验证不了序列化边界，往返测试能直接暴露它。
