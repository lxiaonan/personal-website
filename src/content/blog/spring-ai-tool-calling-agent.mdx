用户问「昨天那批广告为什么失败」，把一个 Java 查询方法标成工具之后，就能回答好了吗？还需要决定参数从哪来、允许查什么，以及失败结果怎样讲给用户。

## S · 背景：自然语言入口不会自动补齐业务身份

任务 ID、项目范围和时间窗口可能缺失。模型还可能把用户说的「所有项目」解释得过宽。接口能查，不代表模型可以拿任意参数去查。

这里以批创状态查询推演 Spring AI 工具设计，不声明这组工具已经上线。

## T · 目标：查询准确，失败也能继续对话

先从只读能力验证参数、权限、日志和返回结构。模型帮助整理请求，服务端决定身份与数据范围。

返回应说明业务阶段和错误，不直接暴露实体、SQL 异常或堆栈。

## A · 行动：收窄工具的输入与输出

### 工具只表达一个动作

例如 `queryBatchCreateStatus(batchId)`，优于含义宽泛的 `operateAdPlatform`。真实名称与类型应跟项目契约一致。

### Schema 与服务端校验各有职责

Schema 描述必填字段、类型、枚举与范围；服务端再校验任务归属、用户权限和时间限制。会话身份来自认证上下文，不能由模型传一个 userId 就决定。

### 返回可解释的摘要

下面仅示意结构，不是真实接口响应：

```json
{
  "status": "PART_SUCCESS",
  "successCount": 8,
  "failedCount": 2,
  "failureSummary": "素材参数不符合媒体要求",
  "retryable": false
}
```

少返回原始载荷，多返回当前阶段、失败原因和下一步需要什么。错误也区分缺参、越权、超时与不可重试。

### 写操作采用独立流程

重提失败项等动作需要明确操作意图、服务端权限、幂等身份和审计。必要的确认应绑定实际对象与参数，不能靠模型一段说明替代。

## R · 结果：模型说了什么，要与系统做了什么对应

使用缺少任务 ID、越权 ID、超出日期范围和服务超时的请求验收。模型不能在工具失败时编造成功，也不能在只读查询里顺手发起重提。

若继续开放写操作，还需检查重复调用、部分成功与操作结果查询。**先让一个小工具能可靠解释，再扩展能力范围。**
