串行太慢，把线程池调大就行吗？媒体接口一旦限流，更多线程可能意味着更多重试。这篇以账号数据拉取为例，推演如何找到可恢复的并发边界。

## S · 背景：账号数量与外部限流同时约束任务

后端可能先取广告主列表，再拉计划、创意、素材或花费。每条创意一个线程容易放大请求；所有账号共用一套限制，又可能让一个媒体拖住其他媒体。

外部系统也会出现 token 失效、网络抖动和服务异常，不能都按「再试一次」处理。

## T · 目标：整批可以结束，失败账号不会消失

目标是在有限时间内拿到可用结果，明确哪些账号失败、为什么失败、是否能单独补跑。并发数、批量大小、超时和重试次数应可配置。

性能改善需要测量，不能由「用了并发」直接推导。

## A · 行动：按业务单元控制资源和恢复

### 账号是可追踪的工作单元

按媒体、账号、接口类型划分预算。线程池或虚拟线程解决执行方式，限流器控制请求速率；二者不是同一个限制。

### 单次与整批都要有超时

HTTP 超时避免单请求挂起，整批截止时间避免无限等待。取消 future 并不总会终止底层请求，写回与外部副作用仍需独立约束。

| 错误 | 处理建议 |
| --- | --- |
| token 失效 | 走受控授权刷新流程 |
| 限流 | 退避并遵守服务商限制 |
| 参数非法 | 记录失败，修参数后再执行 |
| 网络或服务异常 | 有上限地重试，必要时补偿 |

### 入库与补跑共用业务键

花费按日期、账号和媒体对象等维度确定唯一性，使用适合业务的 upsert。日志保留任务批次、账号、接口、错误摘要和成功条数。

## R · 结果：通过失败恢复判断方案是否成立

可以注入一个限流账号、一个参数错误账号和一个慢请求：整批应按截止时间结束，其他账号结果可用，失败项可单独补跑。

补跑同一日期之后，记录数与业务金额不能因重复插入失真。吞吐、延迟和限流次数应一起比较，再决定是否提高并发。

**能解释失败并安全补跑，才有条件继续优化速度。**
