用户只生成了一张图，平台却可能存了两份：一份给用户展示，另一份藏在请求审计的 JSON 里。接口成功返回，反而让这个问题很容易被忽略。

## S · 背景：方便排查的原始响应，包含整张图片

服务商的图像响应可能包含 Base64 数据。把响应原样记入审计，会把大载荷一起写到数据库。页面没有明显异常，存储与处理成本却随请求继续累积。

问题在于把「服务商返回了什么」直接等同于「审计需要保存什么」。

## T · 目标：能排查调用，但不重复保存媒体正文

审计要回答模型、状态、积分和失败原因。图片正文应该由结果与素材链路管理。

这次修复同时要守住展示路径：清理日志不能把用户需要的图片也清理掉。

## A · 行动：递归清理新请求，再处理存量数据

### 清理不能只看最外层

写入审计前递归遍历 JSON，过滤已知 Base64 字段，识别 data URL 并替换为省略标记，保留其他诊断信息。嵌套对象和数组也在处理范围内。

### 展示与审计各走一条路径

给用户的结果保留可用图片数据，给审计的副本收窄为排查信息。不要在共享对象上随意删除字段，导致展示跟着受损。

### 已写入的数据不会自动变小

同次修改补充数据库迁移脚本。验证时分别检查新响应、嵌套字段、历史记录和图片展示，而不只看 Java 方法是否跑通。

## R · 结果：把媒体、业务状态和日志分开保存

2026-07-20 的 `d19fb2679` 包含审计清理与迁移；2026-07-15 的 `d67ad1692` 则处理本地历史重复存图。两个问题都指向持久化边界。

**对象可以被序列化，不代表每个字段都值得长期保存。**
