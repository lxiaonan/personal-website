用户问「为什么点了没反应」，队列监控却显示消息已发送。两边都可能没看错：发送只证明链路走了一步，业务完成还在后面。

## S · 背景：一次操作被拆成了多段提交

批创、历史补算和预计算都适合异步执行。但任务落库、消息发送、消费执行、结果展示不再是一笔天然原子的操作。

任务表提供恢复依据，却不会自动让数据库与消息系统保持一致。

## T · 目标：每个已受理操作都有可查询的去向

接口返回任务身份，页面能查到阶段、错误与结果。重复投递不能重复创建或结算；失败到上限后，也不能悄悄消失。

若有顺序要求，先限定到同一个业务对象，不默认追求全局顺序。

## A · 行动：用业务状态连接投递与消费

### 先处理「落库成功，消息没发」

一种选择是同事务保存任务与 outbox 投递意图，再由发布器发送并重试。发布器也可能重复发送，因此消费仍要幂等。具体方案要结合消息系统的能力选择。

### 消费端根据业务键和状态行动

例如按批次身份查询任务，成功则返回已有结果，处理中需避免重复领取，失败则按规则重试。状态领取与写回需要并发约束。

| 失败类型 | 后续处理 |
| --- | --- |
| 网络、限流、暂时性冲突 | 有上限的退避重试 |
| 参数缺失、权限或配置错误 | 记录原因，修复后再触发 |
| 重试耗尽 | 死信或失败表，提供核对与重放入口 |
| 部分成功 | 保留成功项，只处理失败明细 |

### 排查围绕同一个任务 ID

关联请求、投递、消费、外部调用和业务结果。积压量之外，还要看未完成任务年龄、失败阶段和重试次数。

## R · 结果：恢复路径是异步链路的验收重点

在任务提交后中断发布器、重复消费一条消息、执行中重启消费者，再核对用户能否找到任务、结果是否重复、失败能否恢复。

这些是方案验收条件。采用 MQ 不会自动提供端到端 exactly-once，外部副作用仍需要幂等或核对能力。

**消息状态解释传输，任务状态解释用户操作。两者要能对应起来。**
