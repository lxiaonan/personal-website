- `kind: case-study`：7 篇项目复盘。对应原有证据索引中的修复或交付，R 段列提交、日期和限制。源码、测试与契约交付不等于本轮重新执行了来源项目测试。

- 原始证据继续维护在 `project-content-evidence.md`。

## 一篇文章的契约

前置元数据包含 `title`、`description`、`kind`、`updatedDate`、`star` 与 `takeaways`。`star` 的四个字段为 `situation`、`task`、`action`、`result`；摘要简短，只交代这次问题的关键线索。`takeaways` 写 1–3 个读者可以复用的动作。

正文先用一个具体矛盾引入，再提供四个二级标题：

1. `S · 背景：具体场景`：现象、影响和上下文。
2. `T · 目标：验收标准`：负责范围、约束和想达到的结果。
3. `A · 行动：关键决策`：怎么定位、为什么选这个方案，用三级标题拆步骤。
4. `R · 结果：证据与限制`：复盘提供交付证据；推演提供验证矩阵。

标题开头的字母用于匹配阅读地图的锚点，文章构建后需检查每个地图链接都指向对应标题。Schema 允许未整理文章暂时没有摘要，页面会显示正常正文；新文章按上述结构维护。

段落通常 2–4 句，只加粗决定性结论。字段边界、错误分支、时序对照适合表格；代码应说明是示意还是源码。避免先列一次通用原则、再用长段落重复同样内容。

## 页面阅读路线

- 首页提供三篇精选：Token 结算、CSV 往返、异步视频任务，分别展示成本、输入与状态问题。
- 文章开头提供四段可点击摘要与阅读收获；正文限定阅读宽度，桌面目录跟随，移动端目录折叠。
- 列表、精选与文章使用同一阅读时长估算和内容性质标签。
- 文末按同项目、共同标签与同栏目推荐最多两篇，并给出继续阅读理由。
- 所有站内文章链接经过 `postUrl`，兼容部署 base path；无 JavaScript 时正文与摘要锚点仍可读。

页面优化并不等于留存已经提升。后续应结合实际读者反馈、精选点击与阅读完成情况判断，并迭代内容。

## 工作描述与项目记录

项目页按业务事项组织，不强制套用 STAR 四段。写明负责范围、输入与对象、处理步骤、实际修复、提交依据和验证限制。避免在每个事项后追加“体现了某种能力”的自我评价。

- 用具体动作替换泛化判断：例如“独立提交排队记录后再投递后台”代替“提升异步任务稳定性”。
- 首次调用与重试次数、等待超时与请求取消、提交状态与成功结果分别说明。
- 区分已提交源码、未提交工作区、已有测试意图、本轮执行结果和线上观测。
- 不从项目有某能力推导为个人独立实现，也不从修复代码推导出用户量、收益或成功率。
- 维护依据见 `project-content-evidence.md`，业务与源码细节见 `work-content-record.md`。
